사용자 결정에 따라 기존 카메라 중심 일정을 대체한다. 수동 입력 → 모의 센서 → 실제 온도·습도 센서 → 저장/조회/운영 검증 → 검증된 규칙 기반 확인 안내 → 마지막에 선택적 카메라 유효성 평가 순서로 진행한다. 카메라 성공은 연말 MVP 인수의 필수 조건이 아니다. 스마트팜 적용은 기획 배경으로 유지하며 이번에 농장 운영 전체를 구현하지 않는다.

## 일정 판단 지점

- 11/8까지 실기기 도착일 확인. 미확보 시 모의 경로로 개발하되 실제 센서 검증은 미완료로 남긴다.
- 12/13까지 수동/센서/저장/조회/복구 핵심 기준이 통과하지 못하면 카메라 평가도 다음 단계로 미룬다. 카메라 때문에 핵심 완료를 지연하지 않는다.
- 기존 도메인 담당자의 세그멘테이션 연구는 별도로 계속할 수 있으나 제품팀의 선행 의존성이나 이번 MVP 완료 조건으로 두지 않는다.
- 카메라 단계는 별도 평가 자료로 진행한다. 질병 진단·가지치기 자동 추천·자동 제어는 연말 확정 납품 범위에서 제외한다.
- 공유 서버 선택·비용·접근 정책 확정 후 배포한다. 현재 GitHub Pages는 정적 체험 화면으로 공용 DB/상시 수집 서버가 아니다.

## 연말 필수 인수 시나리오

수동 입력 또는 온도·습도 수신 → 출처·시각과 함께 DB 저장 → 대시보드 현재값/이력 조회 → 누락·오래된 값 확인 → 사용자 관리 기록 → 서버 재시작 및 장애 복구 후 데이터 확인. 실제 장치가 없으면 모의 완료와 실제 미검증을 구분해 보고한다.

## 지속 모의 입력

로컬 API가 실행 중일 때 저장소 루트에서:

```powershell
build/product-venv/Scripts/python -m product.device_contract.seed_demo --url http://127.0.0.1:8018 --live --interval 300
```

최초 14일 모의 이력을 준비한 뒤 온도·습도를 5분마다 DB로 전송한다. 대시보드는 30초마다 조회한다. 전송 실패 시 다음 주기에 재시도하며 실패 기간을 실제 측정값으로 메우지 않는다. PC 종료/절전 중에는 동작하지 않으며 재부팅 후 명령을 다시 실행해야 한다. 실측이나 적정 재배 조건을 의미하지 않는다. 성장/이미지는 초기 fixture이며 이 반복 전송은 센서 두 항목에만 해당한다.

30일 조회의 10,000건 제한을 고려해 기본 간격을 300초로 정했다(30일 약 8,640건). 고빈도 장기 수집 전에는 서버 집계/페이지 처리가 필요하다. GitHub Pages는 배포 시 생성한 정적 모의값이며 이 로컬 입력과 연결되지 않는다.
